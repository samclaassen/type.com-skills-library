# Type runtime

`main.ts` is the saved Bun skill entrypoint (`defineAutomation` from `@type-dot-com/sdk`). Run it with `managed-sandbox/execute_skill_code` and structured arguments. It returns `{ action: "skip", output }`; `skip` only means no follow-up agent turn is requested.

## Arguments

- `config`: see SETUP.md.
- `integrationIds`: `{ bigcommerce, quickbooks?, slack? }` Type connection IDs (`orgint_…`). No tokens.
- `mode`: `preview` (default; reads, renders watermarked `PREVIEW-DO-NOT-IMPORT-*` files, records nothing, posts nothing) or `export` (records each rendered order as `pending` in a batch manifest). There is no execute/post mode.
- `acknowledgeBatch`: `{ batchId, contentSha256 }` exactly as returned by an export. Sent by the running agent after it uploaded every file of that batch folder to Type. Requires `mode: "export"` and no window, polling, `afterOrderId` or `reexportOrderIds`. This is the only call that makes orders `exported`, and the only one that sends the optional Slack summary.
- Fixed window: `since`, `until` (ISO timestamps with offset; filters on BigCommerce `date_modified`), optional `afterOrderId` continuation from the previous result's `nextAfterOrderId`.
- Polling: omit `since`/`until`/`afterOrderId`/`reexportOrderIds` and pass `polling: { bootstrapSince, overlapSeconds = 120, maxWindowSeconds = 86400 }`.
- `timezone`: store IANA timezone (transaction dates are the order creation date in this zone). Aliases such as `Etc/UTC` or `US/Eastern` are accepted; raw offsets such as `+05:00` are rejected. The input schema and the engine use the same check.
- `maxOrders`: 1–100 per run (default 100).
- `reexportOrderIds`: explicit order IDs to export again (fixed window only). Read by ID even outside the window. Refused for orders the journal records as posted. A run plans at most 100 listed + 100 re-export + 200 carried pending orders.
- `slackChannel`: approved channel ID; requires `integrationIds.slack`.
- `outputDir`: absolute parent folder (default `./exports`). Each run writes a new `<outputDir>/<batchId>/` folder; `batchId` = window ID + random run suffix (preview: `PREVIEW-` prefix), so reruns of the same window never share a folder. Whether this sandbox folder outlives the sandbox is a runtime property; that is why the agent must upload it before acknowledging.

Output (prepare): `status` (`preview`, `prepared`, `polled`, `idle` or `blocked` + `reason`), `batchId`, `windowId`, `acknowledge` (`{ batchId, contentSha256 }` or null when the batch has no orders or in preview), `nextStep`, `counts` (`prepared`, `carried`, `notCarried`, `alreadyExported`, `alreadyPosted`, `confirmedPosted`, `awaitingConfirmation`, `review`, `paymentFollowUps`), `supersedes`, `carried`, `notCarried`, `acknowledgedBatchesCompleted` (only when present: acknowledged batches whose orders this run recorded as exported because the acknowledging call did not finish them; also on `blocked` results, in `nextStep` and in `summary.md`), per-order `orders` outcomes (`pending_acknowledgement`, `already_exported`, …), `reviewQueue`, `qbo` check status and warnings, `warnings`, `cursorAdvanceSafe`, `nextAfterOrderId`, and `delivery` (`directory`, and per file: name, path, bytes, rows, SHA-256). **File contents are never returned.**

Output (acknowledge): `status: "acknowledged"` (or `blocked` + `reason`), `batchId`, `contentSha256`, `alreadyAcknowledged`, `counts` (`orders`, `invoices`, `salesReceipts`, `invoiceThenPayment`, `recordsCompleted`), `notification`, `warnings`, `nextStep`.

Result size: the Type SDK rejects results over 64 KiB. Every result is checked against a 48 KiB budget before it is returned. Over budget, per-order lists are truncated (with `<list>Omitted` counts), then the file list is replaced by `fileCount`, `totalBytes` and `manifestPath`, and as a last resort only status, batch identity, `acknowledge` and counts remain (`truncated: true`). The batch folder's `manifest.json` always has the full file list. A 100-order × 1-line export returns about 8 KB; 100 orders × 500 lines (100 invoice files) about 30 KB. Because nothing is exported before acknowledgement, even a failed result loses no order.

## Provider boundary

- BigCommerce: `type.integrations.request` with `method: "GET"` hard-coded; the port has no method parameter. Paths must start with `/stores/<storeHash>/` and cannot contain `..`, `?`, `#`, `%` or `\`. 429 responses are retried up to 3 times when `Retry-After` ≤ 10 s. Truncated responses are failures.
- QuickBooks: `type.tools.call` with service `quickbooks`, limited to `quickbooks_get_company_info`, `quickbooks_list_entities`, `quickbooks_get_entity`, `quickbooks_run_report`. Anything else is refused before any request. Paging requests `maxResults` 100 and advances by the rows actually returned minus a 5-row overlap, bounded by `config.qboLimits`; reaching the bound marks the list incomplete.
- Slack: `slack_post_message` to the bound channel, only when a batch is acknowledged, at most once per batch (create-only claim). It sends counts and the batch ID only and says the files were uploaded to Type, not to Slack. A send without a `status: "sent"` receipt is reported as `outcome_unknown` and not repeated.
- QuickBooks paging is verified: each page re-reads the last 5 rows of the previous page, which must match exactly; a mismatch is retried once, then blocks (`qbo_<entity>_paging_inconsistent`). New rows after a page of 5 rows or fewer cannot get the full overlap, so the list is reported incomplete. Residual: a delete plus an insert before the same page boundary between two page reads is not detected (the overlap rows still match). `quickbooks_get_entity` (Invoice by Id) is used for targeted checks of invoices the journal records as posted.
- Python (`main.py`) is a pure planner: Bun spawns `python3 -I main.py` with no shell, a fixed 3-variable environment (no credentials), JSON on stdin/stdout, at most 400 orders and a 60 s deadline. Input is projected to the fields the planner reads (order money/status fields, billing address fields, product sku/name/quantity/price/tax/refund/discount fields; QuickBooks customers Id/DisplayName/Active/email/currency; vendors DisplayName/Active) and bounded: 2 MiB per order (above → durable `order_too_large_for_planner` review), 64 MiB per run (a page that does not fit ends early; the cursor continues from the last planned order), 128 MiB output.
- QuickBooks retries: up to 3 attempts for retryable errors, backing off 2 s then 4 s between attempts (never after the last).

## Journal (Type recorded data, space scope)

All writes use `type.data.record(key, value, { scope: "space", expectedVersion })` (compare-and-swap); reads use `type.data.read`. Preview mode refuses every write in the adapter itself.

- `bcqbo/<store>/order/<orderId>` (schema 3): `{ state: pending | exported | confirmed_posted | needs_review, sourceHash, pendingBatch?: { kind, docNumber, customerName, totalCents, currency, batchId, rowHash, runId }, export?: { kind, docNumber, customerName, totalCents, currency, batchId, exportCount }, qboInvoiceId?, reason?, paymentFollowUp?, readFailures? }`. `pendingBatch` is the newest unacknowledged batch holding the order's rows; `export` is the last acknowledged export. A `qboInvoiceId` is kept through later reviews, so a posted order is never exported again.
- `bcqbo/<store>/batch/<batchId>`: batch manifest `{ status: prepared | superseded | void | acknowledged, orders: [{ orderId, rowHash, kind }], files: [{ name, bytes, sha256, rows }], contentSha256, supersedes, supersededBy?, acknowledgedAt? }`. Created once per export batch with orders. `contentSha256` = SHA-256 of the batch ID, every order's row hash and every file's SHA-256. Only `prepared` → `acknowledged` (the acknowledgement) or `prepared` → `superseded` (a later run that re-renders its orders) or `prepared` → `void` (folder write failed) transitions exist, each by compare-and-swap, so a batch is never both acknowledged and superseded.
- `bcqbo/<store>/pending`: follow-up index, max 1,000 order IDs: pending (unacknowledged) orders and exported invoices awaiting confirmation. New orders are added before their pending record is written. Beyond 1,000, new orders go to review with `confirmation_backlog_full`; beyond 200 pending orders, with `unacknowledged_backlog_full`. Each run reads every indexed record.
- `bcqbo/<store>/poll`: polling checkpoint `{ bindingHash, completedThrough, window }`.
- `bcqbo/<store>/summary/<batchId>`: create-only claim so one Slack summary is sent per acknowledged batch.

`sourceHash` covers money fields, buyer email, transaction date and product lines. Fulfilment or payment-capture changes do not alter it. A different hash after export → `changed_after_export` review; after a pre-existing QuickBooks posting → `changed_after_posted_in_qbo`. Records written by 3.0.x candidates (schema 2, `pending_export`) are not read by 3.1 (they are reported as `journal_record_invalid` on every run that sees the order; the record is never overwritten and the order is never rendered as new); no 3.0.x candidate was used with live data. A batch manifest that is present but no longer parses is treated as unknown (`batch_state_unknown`, cursor held), never as missing.

## Polling

`scheduler.ts` commits a fixed window (`since`, `until`, `afterOrderId`) before reading, resumes it on the next invocation, and advances only when the batch is `prepared` with `cursorAdvanceSafe: true` for the same window (every order of the window has a durable record; acknowledgement is not required because pending orders are carried by the index). After each poll the agent uploads and acknowledges the returned batch in a separate call (SKILL.md). Orders that can never be read safely get a durable review record and do not hold the window (EXECUTION.md, Failures). A full page keeps the window and moves the ID cursor; a finished window starts the next one with `overlapSeconds` overlap (already-exported orders in the overlap are skipped by the journal). Changing configuration, timezone, connections or polling settings blocks with `poll_configuration_changed_requires_review`. Preview polling writes no checkpoint.

To run "export new orders since last run" on a schedule, a user-approved scheduled managed-agent task would invoke this saved skill with `mode: "export"` and `polling`, then upload the batch folder and call `acknowledgeBatch`. A scheduled run that only polls (never acknowledges) keeps re-rendering the same pending orders and, after 200 of them, sends new orders to review. This package creates no schedule. Run one poller per store and do not overlap runs for the same store.

Request budget: QuickJS automations are documented with 128 Type API requests per invocation; this Bun skill run through `execute_skill_code` issues more (up to 1,000 index record reads, one write per rendered order, BigCommerce reads per order). Whether `execute_skill_code` has a similar budget was not verified.
